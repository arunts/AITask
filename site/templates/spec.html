AITaskDefinition file format

A task file is a small JSON text file that holds one task: its prompts, the values it asks for, and the tools the model may use. This page is the complete reference for version 1 of the format, as read and written by AITaskRunner $version.

On this page

Also available as the skill's reference.

Overview

The app reads and writes task files with a tolerant decoder: unknown keys are ignored and missing optional keys take their defaults, so a file written by hand can be as short as the required fields. Strict JSON: double quotes, no trailing commas, no comments. UTF-8. Line breaks inside a prompt are written as \n.

Not in the file, because they are choices about your Mac rather than about the task: which model runs it, generation settings such as temperature, its schedule, and any run history.

A complete example

{
  "format": "AITaskDefinition",
  "version": 1,
  "task": {
    "name": "Summarise Notes Folder",
    "systemPrompt": "You are a concise technical writer. Reply in Markdown.",
    "userPrompt": "1. Run shell__run with: find \"{{notes_folder}}\" -maxdepth 1 -name '*.md'\n2. Read each file with: cat \"<path>\"\n3. Write a summary to {{notes_folder}}/SUMMARY.md with: cat > file <<'EOF'",
    "allowsSteering": false,
    "requires": ["tools"],
    "variables": [
      { "key": "notes_folder", "type": "folder", "default": "~/Notes", "description": "Folder to summarise" },
      { "key": "topics", "type": "list", "options": ["weather", "sport"], "description": "Topics to cover" }
    ],
    "tools": [
      { "builtin": "shell" },
      { "server": "fetch", "tools": null }
    ]
  },
  "mcpServers": {
    "fetch": { "type": "stdio", "command": "uvx", "args": ["mcp-server-fetch"] }
  }
}

Variables

A variable is a blank the task asks you to fill in each time it runs, such as a folder or a topic. In the prompts you refer to it as {{key}} (spaces inside the braces are tolerated), and the app swaps in the value before the model sees anything.

KeyTypeDefaultNotes
keystring—Required. The name used inside {{ }}. Sanitized on import: letters, digits, _, . and - are kept, whitespace becomes _, anything else is dropped. An entry whose key becomes empty is dropped.
type"text" · "file" · "folder" · "list""text"file and folder show a Choose… button in the run sheet. list holds several values at once. Unknown values fall back to text.
defaultstring""Pre-filled in the run sheet; the value last used is remembered. defaultValue is accepted as an alias. Ignored for lists.
optionsarray of strings[]Lists only: the values, at most 100. Blanks and repeats are dropped. In the prompt {{key}} becomes all of them joined with , . Values added or removed while running are saved back onto the task.
descriptionstring""One line shown under the field. Say what to enter.

A {{placeholder}} with no matching variable is left in the prompt as-is and sent to the model as literal text. Keep the two in step. Paths are substituted exactly as typed; ~ is fine because the shell expands it.

Prefer a folder or file variable over asking the model to guess a path, and a default that makes the task runnable without typing anything. Use a list for a set of values that grows over time: topics to cover, feeds to check, languages to translate into.

Tools

Each entry in tools attaches one source of tools. Exactly one of builtin or server:

{ "builtin": "shell" }
{ "server": "fetch", "tools": null }
{ "server": "github", "tools": ["search_issues", "get_issue"] }
KeyNotes
builtinA pack that ships inside the app: "shell" or "context". Unknown packs are refused. "bash", the shell pack's old name, is still accepted and treated as shell.
serverThe slug of an MCP server defined under mcpServers, or of one the user already has in the app.
toolsThe exact tool names to expose, as an array. null or omitted means every tool the source offers, including ones added later. Unknown built-in tool names are refused. MCP tool names cannot be checked at import time, so spell them exactly as the server reports them. Fewer tools help small models choose well.

The model sees each tool as source__tool: shell__run, context__clear, fetch__fetch. Use those exact names in the prompts. The app highlights them, and small models follow explicit names far more reliably than descriptions. Order matters only for display; attaching the same source twice is pointless, and the last entry wins.

Model requirements

A task can say what the model must be able to do. The app never runs it on a model known to lack one of these, marks such models in the picker, turns Run off for them, and holds a scheduled run until the chosen model qualifies.

"requires": ["tools", "vision"]
NameMeansWhen to list it
toolsThe model can call tools.Never needed by hand: it is assumed whenever tools is non-empty or allowsSteering is true. Listing it is harmless, and the app writes it on export.
visionThe model accepts image input, so it sees the images tools return instead of a text placeholder.The job depends on looking at screenshots, rendered pages, charts or photos that a tool returns.
thinkingThe model reasons before it answers (Qwen3, DeepSeek-R1, gpt-oss, Gemma 4 and other “thinking” models).The job needs multi-step reasoning that plain instruction-tuned models get wrong. The app does not turn thinking on; it only limits which models are offered.

How the app knows what a model supports: Ollama reports all three for each model; LM Studio and llama.cpp report vision; and a run teaches it (a rejected image or tool request, a tool call that came back). A model whose server reports nothing is allowed to run, with a note in the transcript. When vision is required and the server rejects the images anyway, the run ends instead of going on without them.

Built-in tools

Two packs, Shell (shell__run) and Context (context__clear). Nothing to install. Either can be turned off in the app; a task that needs it still imports, with a warning, and fails at run time until it is turned back on.

ToolWhat it doesArguments
shell__runRuns a command line in the user's login shell (zsh -l -c) and returns the command, working directory, exit code, timing, stdout and stderr. Output is truncated at about 30 000 characters. A non-zero exit is reported as a tool error the model can react to.command (required), working_directory (default: the folder set in the app), timeout_seconds (default from Settings, 60; maximum 600)

Every command is shown for approval before it runs (Deny, Allow, or Allow All This Run) unless approval is turned off. In a scheduled run, commands run without asking. Commands are not confined to any folder; they can reach anything the user's account can. Write destructive jobs so the prompt uses the Trash rather than rm.

Working with files goes through the shell: ls, cat, find, grep, mv, and a heredoc (cat > file <<'EOF') to write. Quote paths in the commands you write into the prompt, so spaces in folder names do not break them.

context__clear

ToolWhat it doesArguments
context__clearDrops everything in the conversation except the system prompt, the task's user prompt and the note passed in; the model continues from a tool result that repeats the note. For runs that work through many large files or items one at a time, where each item would otherwise stay in the context window. A blank note clears nothing. Tool calls issued after it in the same reply still run. The round limit restarts. Skipped on the Apple on-device model.note (required): what is done, what comes next, and anything not yet saved

Attach it with { "builtin": "context" }. Have the prompt save each item's output to disk before calling it, and put the remaining items in the note: after a clear the model remembers nothing else.

ask_user

Not listed in tools. When allowsSteering is true the app adds it automatically. It shows a question in the run window and suspends the run until the user answers or stops it. One argument: question. Tell the model when to use it (“ask_user before any destructive step”) and when not to.

MCP servers

For anything the shell cannot do well, such as fetching web pages or talking to a service, a task can use an MCP server. Define it under mcpServers in the same shape Claude Desktop, Cursor, VS Code and Claude Code use. The key is the server's name; its slug is what tools[].server refers to.

Slug rule: lowercase the name; keep ASCII letters, digits and -; every other run of characters becomes a single _; trim _ and - from both ends. "Brave Search" → brave_search. A definition may carry its own "name", which then replaces the key for both display and slug. Do not use shell, bash or context as a slug; they belong to the built-in packs.

A server started as a local program

"fetch": {
  "type": "stdio",
  "command": "uvx",
  "args": ["mcp-server-fetch"],
  "env": { "SOME_FLAG": "1" }
}
  • command is required. It is resolved through the user's login-shell PATH, so npx, uvx, node and python3 work when installed.
  • args: an array of strings (preferred) or one shell-style string.
  • env: an object of string values. Optional.

A server reached over HTTP

"docs": {
  "type": "http",
  "url": "https://mcp.example.com/mcp",
  "headers": { "Authorization": "Bearer REPLACE_ME" }
}
  • url is required. type may also be "streamable-http" or "sse".
  • headers: an object of string values. Optional. The app sends static headers only; a server that needs an OAuth login flow will not work.
  • Without type, a definition with command is stdio and one with only url is HTTP.

Keep API keys out of shared files. Leave env and headers out and add them in the app after importing. Where a header is structurally required, use an obvious placeholder such as REPLACE_ME.

If the user already has a server with the same slug, the app reuses theirs and ignores the definition in the file. Otherwise the definition is added to the app with a fresh ID. Definitions that no tools[] entry references are ignored.

How tool results reach the model

  • Text content is joined and sent as the tool result. A result longer than about 60 000 characters is cut with a note.
  • MCP image content (and embedded resources with an image/* blob; PNG, JPEG, WebP, GIF) is kept. An OpenAI-compatible model receives the images as image_url parts in a follow-up user message right after the tool result; the tool result itself keeps a numbered placeholder such as [image 1: image/png]. About 24 MB of image data per result is forwarded; the rest is dropped with a note.
  • A model without vision (the server rejects the images) gets the placeholder plus a note that images are not shown; the app switches to text-only for the rest of the run and says so in the transcript. Some servers silently ignore images instead of rejecting them. When the task requires vision, a rejected image ends the run instead.
  • The Apple on-device model never receives images; it gets the placeholder and a note.
  • Images returned by tools appear as thumbnails under the tool call in the run window.

What happens on import

The preview shows the task, its variables, its tools, and which servers will be added or reused. Nothing is changed until the import is confirmed.

Refused

  • Missing "format": "AITaskDefinition" (or the legacy name), a version outside 1…1, or no task object.
  • An empty task.userPrompt.
  • A tools[] entry that is neither builtin nor server, an unknown built-in pack, or an unknown built-in tool name.
  • A server slug with no definition under mcpServers, unless a server with that slug already exists in the app.
  • An mcpServers definition without command (stdio) or url (HTTP).

Imports with a warning

  • The Shell pack is turned off in the app.
  • A list variable has more than 100 options; only the first 100 are kept.
  • A name in requires other than tools, vision or thinking; it is dropped.

Goes wrong silently

  • A {{placeholder}} with no matching variable is sent to the model as literal text.
  • A variable key that needed sanitizing no longer matches the spelling used in the prompts.
  • tools[].server spelled differently from the slug of its mcpServers key. Lowercase keys avoid surprises.
  • A prompt that says bash__run: the app accepts "builtin": "bash", but the tool the model sees is shell__run.
  • ask_user mentioned in a prompt while allowsSteering is false; the model will not have that tool.

How the app exports

Exporting a task writes exactly this format. env and headers are left out unless “Include environment variables and HTTP headers” is ticked. Variables of type text carry their default; lists carry their options. requires holds everything the task needs, tools included whenever a tool is attached. Round-tripping a file through export and import is lossless apart from those secrets and the per-machine fields listed at the top.

Validating by hand

The authoring skill ships a standard-library Python script that mirrors the importer and prints a preview. Exit code 0 means the app will import the file; 1 lists the errors; warnings never block.

python3 ai-task-author/scripts/validate_task.py "My Task.json"

Inside the app, the task summary shows the tools the prompts name and flags any that are not attached, and the context section measures what the prompts and tool definitions cost against the chosen model's window.

Checklist before sharing a file

  1. format, version and task.userPrompt present.
  2. Every {{placeholder}} has a variable, and every variable is used.
  3. Every tools[].server has a matching mcpServers slug.
  4. Every tool name mentioned in the prompts is attached: shell__run needs the shell entry.
  5. ask_user mentioned only when allowsSteering is true.
  6. requires lists vision when the job depends on images a tool returns, and thinking only when a reasoning model is a must.
  7. No secrets in env or headers.
  8. The validator exits 0.

Tips: start from an exported task and change it rather than typing from scratch. One thing per task, numbered steps, the tool names spelled out. Small local models follow that far better than prose, and Apple's on-device model has a window of roughly 4 000 tokens.
